= Plurimath testsuite

== Purpose

Conformance tests for https://github.com/plurimath/plurimath[Plurimath]
implementations, encoded as data rather than code.

The Ruby gem's expectations currently live inside its own spec files, where
only Ruby can read them. This repository holds the same knowledge as YAML, so
every implementation — the Ruby gem, the TypeScript port, and any future one —
can be checked against identical answers.

== What is covered

Early. AsciiMath input is the first notation extracted, and the only one so
far. A tick means cases exist here today, not that Plurimath supports it —
Plurimath supports every row.

[cols="1,2,2",options="header"]
|===
| Notation | As input | As output

| AsciiMath   | ✅ 92 cases, 19 groups | ✅ checked for all 92
| LaTeX       | ❌ no cases yet        | ✅ checked for all 92
| MathML      | ❌ no cases yet        | ✅ checked for all 92
| OMML        | ❌ no cases yet        | ❌ no cases yet
| UnicodeMath | ❌ no cases yet        | ✅ checked for all 92, one a refusal
| HTML        | ❌ no cases yet        | ❌ no cases yet
|===

Every case carries an expectation for every output format above that is
ticked. An expectation is usually a rendering; one of them is a refusal, and
the section on outcome payloads below says why that is recorded rather than
omitted.

Groups, and the cases in each:

`numbers` 5, `symbols` 7, `operators` 6, `fences` 6, `frac` 6, `powers` 8,
`roots` 4, `unary-functions` 7, `quoted-text` 3, `nary` 6, `matrices` 2,
`mixed` 5, `permissive` 6, `fonts` 7, `colour` 2, `left-right` 3,
`mod` 3, `whitespace` 5, `partial-render` 1.

`scripts/validate.rb` checks these numbers against the corpus, so they cannot
drift again — they had already drifted twice before the check existed.

== Using it

Consumers pin this repository — as a git submodule, or however their language
prefers — and read the YAML directly. Each payload names the schema it follows,
and `corpus/provenance.yaml` records which gem commit produced everything,
along with a checksum per payload so a consumer can tell whether a file has
been edited by hand.

There is no build step and no published package. The YAML is the artifact.

== Format

There are three kinds of payload. A **case** records one input and what
Plurimath produced for it:

[source,yaml]
----
- id: frac-simple
  input: a/b
  input_format: asciimath
  preprocessed: a/b
  expected:
    asciimath: frac(a)(b)
    latex: "\\frac{a}{b}"
    mathml: |
      <math xmlns="http://www.w3.org/1998/Math/MathML" display="block">
        <mstyle displaystyle="true">
          <mfrac>
            <mi>a</mi>
            <mi>b</mi>
          </mfrac>
        </mstyle>
      </math>
    unicodemath: "(a)/(b)"
  parse_tree:
    expr:
      frac:
        numerator:
          symbol: a
        denominator:
          sequence:
            symbol: b
  model:
    class: Math::Formula
    fields:
      displaystyle: true
      input_string: a/b
      left_right_wrapper: true
      value:
      - class: Math::Function::Frac
        fields:
          parameter_one:
            class: Math::Symbols::Symbol
            fields:
              value: a
          parameter_two:
            class: Math::Symbols::Symbol
            fields:
              value: b
----

`id`:: stable identifier for the case
`input`:: the source expression
`input_format`:: the notation `input` is written in
`preprocessed`:: `input` after the reader's preprocessing pass — what the
grammar is actually handed
`expected`:: expected output, keyed by target format
`parse_tree`:: what the grammar produced, before it became a model
`model`:: the parsed expression as a tree of nodes

An implementation reads these files and asserts its own output matches.

=== Rejection payloads

The other kind. A **rejection** records an input Plurimath *refuses*, so an
implementation can be checked on what it must not accept. A corpus of successes
alone cannot do that: an implementation that returns something plausible
wherever the gem raises passes every case above and is still wrong.

They live beside the cases, at `<input-format>/rejections.yaml`, and declare
`schema: plurimath-corpus/rejections/1` — a payload *kind*, like `provenance`,
with the format carried in the payload's own `input_format`.

[source,yaml]
----
schema: plurimath-corpus/rejections/1
group: rejections
input_format: asciimath
cases:
- id: frac-trailing
  input: a/
  input_format: asciimath
  preprocessed: a/
  error:
    category: parse_error
    index: 1
----

A rejection has no `targets`, no `expected`, no `parse_tree` and no `model`,
because nothing parsed and nothing was rendered.

`error.category`:: what the gem raised. `parse_error` is the only value, and
deliberately so: `Plurimath::Math.parse` rescues everything and re-raises
`Math::ParseError`, so from outside a grammar failure cannot be told apart from
any other parse-time failure. The gem's other errors come from bad *arguments*
rather than bad input, which this corpus does not cover.
`error.index`:: optional. A character offset into `preprocessed` — **not** into
`input` — because preprocessing rewrites `{:` and friends to single characters
and shifts every later offset. An implementation maps it back through its own
offset map. Absent when the failure did not come from the grammar.

An implementation is conformant when it refuses every one of these. Asserting
the offset is a stronger claim and needs that mapping; asserting the refusal
alone is a valid, weaker conformance.

=== Outcome payloads

The third kind. Some inputs Plurimath **accepts** render to only some of the
targets. `sqrt(` is one: it parses, it renders to AsciiMath, LaTeX and MathML,
and `to_unicodemath` raises.

The case shape above cannot hold that. A group declares one `targets` list and
every case must carry an expectation for every target in it, so an input like
this had nowhere to go and was left out. Leaving it out is not neutral: an
implementation that refuses `sqrt(` outright passes every case in the corpus
and is still wrong about an input the gem accepts.

Such groups declare `plurimath-corpus/<input-format>/2` instead, and there
each target carries an **outcome** — exactly one of a rendering or a refusal:

[source,yaml]
----
schema: plurimath-corpus/asciimath/2
group: partial-render
input_format: asciimath
targets:
- asciimath
- latex
- mathml
- unicodemath
cases:
- id: partial-sqrt-unclosed
  input: sqrt(
  input_format: asciimath
  preprocessed: sqrt(
  expected:
    asciimath:
      output: sqrt
    latex:
      output: "\\sqrt{}"
    mathml:
      output: |
        <math xmlns="http://www.w3.org/1998/Math/MathML" display="block">
          <mstyle displaystyle="true">
            <msqrt/>
          </mstyle>
        </math>
    unicodemath:
      error:
        category: parse_error
  parse_tree: ...
  model: ...
----

`output`:: exactly the bytes the gem produced, as in a case above.
`error.category`:: the target refused to render. `parse_error` is the only
value, for the same reason it is in a rejection: `Math::Formula#to_unicodemath`
and its siblings funnel render failures through `wrap_render_error`, which
re-raises `Math::ParseError` — measured on `sqrt(`, the underlying
`NoMethodError` survives only as `#cause`. The category names what the public
boundary says, so it stays portable; which target refused, and at which
operation, is already said by the key the outcome sits under.

There is no `index` here. An offset would point into `preprocessed`, and by
the time a target renders, `preprocessed` has already parsed: the refusal is
downstream of the text, and no position in it describes the failure.

`parse_tree` and `model` are still required, and still mean what they mean
above. The input parsed, so there is a tree and a model to reproduce; only the
rendering of that model failed.

The schemas use `oneOf` with `additionalProperties: false` in both branches, so
an outcome carrying both keys is refused and so is an empty one. Two states,
exhaustive and exclusive, with no third for an implementation to slip through.

This is additive. Nothing in `cases/1` was converted, and `cases/1` is not
deprecated: a group whose every case renders to every target stays there and
stays byte-for-byte what it was. A payload names its own schema, and
`scripts/validate.rb` dispatches on that name, so both kinds sit in the corpus
side by side. A consumer that understands only `cases/1` keeps working
untouched — it reads the groups it already read, and skips the ones declaring
a schema it does not know.

=== What `model:` means

A `model:` block is a node's *portable semantic state* — the fields any
implementation must reproduce to be equivalent — and not a dump of every Ruby
instance variable the gem happens to carry.

The two usually coincide, so the generator reads the instance variables. Where
they do not, `scripts/generate-corpus.rb` declares that class's portable state
explicitly, in `MODEL_PROJECTIONS`, and the declaration is the contract.
`Math::Function::Unitsml` is the standing case: it caches a parsed
`Unitsml::Formula` beside the `text` it was built from, and only `text` is
state — the gem itself compares and clones by `text` alone.

A field absent from a `model:` block is therefore absent by decision, not by
accident. An implementation is conformant when it reproduces every field that
is present; how it represents anything else is its own business.

== Layout

`corpus/`:: the test cases, grouped by feature
`corpus/provenance.yaml`:: how every payload was produced — gem commit, Ruby
version, generator checksum, and a `sha256` and byte count per payload
`schema/`:: JSON Schema describing the file formats, validated in CI
`scripts/generate-corpus.rb`:: writes the corpus from the Ruby gem
`scripts/validate.rb`:: checks the corpus against the schemas, and checks what
a schema cannot — that every payload is recorded, and that each one still
hashes to what `provenance.yaml` says
